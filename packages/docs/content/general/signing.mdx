# Signature Scoping

Some integrations require a Safe to produce a signature rather than execute a transaction — for example, signing a CowSwap order, a Permit2 approval, or a Sign-In with Ethereum (SIWE) message.
Because a Safe is a smart contract and cannot use a private key to sign, signatures are produced by writing to the Safe's [`signedMessages`](https://github.com/safe-global/safe-smart-account/blob/main/contracts/Safe.sol) storage and validated through [EIP-1271](https://eips.ethereum.org/EIPS/eip-1271).

Marking a message as signed is itself a state-changing call from the Safe.
The Roles Modifier scopes these signing calls just like any other transaction, but the data being checked is the message that's about to be signed rather than the parameters of an external call.

## How signing works

Signing is implemented by a small `SignTypedMessageLib` library that the Safe invokes via delegatecall.
The library exposes two entry points relevant to scoping:

- `signTypedMessage(domain, message, types)` — for [EIP-712](https://eips.ethereum.org/EIPS/eip-712) typed structured data
- `personalSign(message)` — for [EIP-191](https://eips.ethereum.org/EIPS/eip-191) `personal_sign` text messages

Each entry point computes the same `SafeMessage` hash that EIP-1271 verification expects, then sets `signedMessages[hash] = 1` in the Safe's storage.
After this, calling `isValidSignature(hash, "0x")` on the Safe returns the EIP-1271 magic value, so any verifier that follows the standard accepts the signature.

Because the call originates from the role member and goes through the Roles Modifier, the modifier's conditions decide whether the signing call is allowed at all.
That is the surface signature scoping operates on.

## EIP-712 typed messages

EIP-712 messages are structured: a domain separator pins the signature to a specific app and chain, and a typed message tree describes the payload.
Scoping a typed message means expressing constraints over those structured fields — for example "only allow CowSwap orders where the receiver is the avatar".

To make this practical, `SignTypedMessageLib` does the EIP-712 encoding on-chain.
Roles permissions then evaluate ordinary [conditions](/general/conditions) against the ABI-encoded `domain` and `message` blocks.
A field-level constraint on a typed message becomes a condition on the corresponding position in the encoded payload.

### Selector aliases

A single Roles Modifier permission targets a function by its 4-byte selector.
But a Safe may want to sign multiple unrelated EIP-712 layouts (e.g. CowSwap orders _and_ Permit2 approvals) under different conditions.

To allow this, `SignTypedMessageLib` accepts `signTypedMessage` calls under any selector via a Solidity `fallback`.
The SDK derives a selector deterministically from the EIP-712 type definition (the keccak hash of its encoded type tree, truncated to 4 bytes), so each distinct typed-data layout gets its own permission entry.
Two permissions for two layouts coexist without conflict.

### Type integrity

The `types` argument of `signTypedMessage` describes the layout the encoder uses to walk the `domain` and `message` bytes.
A malicious caller could try to pass a different `types` argument that re-interprets the same bytes as a different structure.
To prevent this, the scoped condition pins `types` to an exact value so only the layout the permission was authored for is accepted.

## `personal_sign` messages

`personal_sign` messages are unstructured text wrapped with the EIP-191 prefix `\x19Ethereum Signed Message:\n<length>`.
There is no domain separator and no field tree to constrain — the only thing a permission can meaningfully match against is the message text itself.

The `personalSign(bytes)` entry point handles the EIP-191 wrapping internally, so the scoped condition operates on the raw message bytes.
The SDK's prefix scoping uses a [bitmask](/general/conditions#bitmask) condition that requires the message to start with a given string.

This is enough for most real-world use cases:

- **SIWE messages** start with `"<domain> wants you to sign in with your Ethereum account"`, so pinning the domain prefix prevents phishing across hosts.
- **App-specific session messages** typically start with a fixed marker that identifies the application.

The trailing portion of the message (nonces, timestamps, session IDs) is not constrained, since those are effectively single-use values that the verifying app is expected to validate.

## What a signature authorizes

A signature from the Safe is accepted wherever the Safe's EIP-1271 signature counts.
That includes every contract that authenticates the Safe by signature: the apps the permission is meant for, but also any Roles Modifier where the Safe is a member (its `execTransactionWithSignature` takes EIP-1271 signatures), and any Safe that has this Safe as an owner.
A signing permission therefore grants whatever the signed message authorizes in those places, not just in the intended app.

Scope signing permissions as tightly as execution permissions:

- Do not allow `SignTypedMessageLib.signMessage`. It signs a raw 32-byte hash, and a condition on a hash cannot tell what was hashed: allowing it, with any condition other than pinning exact hashes, lets the role sign anything, including transactions of other Roles Modifiers and Safes.
- Do not allow `SignTypedMessageLib` as a whole target, or a `signTypedMessage` selector without pinning `types`: the library accepts typed messages under any selector, so either allows any typed message.
- Constrain the EIP-712 domain (`chainId`, `verifyingContract`) of typed-message permissions. With the types pinned but the domain open, the role can sign that message type for every contract that uses it.

`personalSign` cannot produce an EIP-712 signature: the EIP-191 prefix makes its hash differ from every EIP-712 digest.

The SDK's `permissionHazards(targets)` flags these permissions, along with delegatecall permissions and permissions on the Roles Modifier itself.
