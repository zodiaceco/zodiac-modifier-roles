# Transaction Unwrapping

In certain scenarios, the raw transaction data might not lend itself to be checked against the configured role permissions directly.
An example are batch transactions through the [MultiSend contract](https://github.com/safe-global/safe-smart-account/blob/main/contracts/libraries/MultiSendCallOnly.sol).
Instead of scoping the data encoding the full batch of transactions, permissions should be checked individually for each call in the batch.

Transaction unwrapping can be configured as a pre-processing step to be applied for specific target addresses.
The unwrapping logic is implemented in adapter contracts.

## `MultiSendUnwrapper`

The `MultiSendUnwrapper` adapter contract at the official deployment address `0xB4Cd4bb764C089f20DA18700CE8bc5e49F369efD` can be used to support unwrapping of batch transaction through the [MultiSend contract](https://github.com/safe-global/safe-smart-account/blob/main/contracts/libraries/MultiSendCallOnly.sol).

To enable multi-send unwrapping call the `setTransactionUnwrapper` function as the owner of the Roles mod:

```solidity
rolesMod.setTransactionUnwrapper(
    address(0x9641d764fc13c8B624c04430C7356C1C7C8102e2)),  // offical MultiSendCallOnly deployment on mainnet
    bytes4(keccak256('multiSend(bytes)'),  // multiSend function selectot
    address(0xB4Cd4bb764C089f20DA18700CE8bc5e49F369efD)  // address of the MultiSendUnwrapper
)
```

Addresses of the official MultiSend deployments on all chains are listed at https://github.com/safe-global/safe-deployments.

### How a batch is checked

- Each transaction of the batch must pass its own permission: the target or function entry for it, its execution options (value, delegatecall), and its condition on its own calldata. The batch passes only if every transaction does.
- All transactions are checked before any of them executes. Conditions that read state outside the calldata (custom conditions, `WithinRatio`, price adapters) see that state as it was before the batch, for every transaction in it, not as earlier transactions of the batch leave it.
- Allowances are charged across the whole batch: two transactions metered by the same allowance draw from one balance, and the batch is settled once, after it executed.
- A batch inside a batch (a transaction of the batch that delegatecalls `MultiSend`) is not unwrapped. It is checked as a single delegatecall against the role's permission on `MultiSend`, and the transactions inside it are not checked one by one.

## Custom unwrappers

Custom transaction unwrapping logic can be implemented as contracts conforming to the `ITransactionUnwrapper` interface.

```solidity
struct UnwrappedTransaction {
    Operation operation;
    address to;
    uint256 value;
    uint256 dataLocation;
    uint256 dataSize;
}

interface ITransactionUnwrapper {
    function unwrap(
        address to,
        uint256 value,
        bytes calldata data,
        Operation operation
    ) external view returns (UnwrappedTransaction[] memory result);
}
```

The `UnwrappedTransaction` struct uses `dataLocation` and `dataSize` to reference a slice of the original calldata rather than copying the data bytes.
This design avoids unnecessary memory allocation when unwrapping batch transactions.

Roles checks the transactions the unwrapper returns and never the call itself. An unwrapper must therefore return exactly the transactions its target executes for that calldata, on any calldata, also malformed: anything the target executes that the unwrapper leaves out runs unchecked.
